# OSS 文件强一致同步设计

## 问题

工作台编辑器的“已保存”只证明浏览器本地内容保存成功。旧链路由浏览器取得签名后直接 PUT，未在保存完成后回读 OSS 对象，也没有保证当前文件和唯一 objectKey 的绑定，因此可能出现同名对象重复、云端仍为旧内容、页面却显示成功。

## 方案

- 工作台继续在浏览器中生成 DOCX/XLSX/TXT 文件内容。
- 所有上传统一调用同源 `PUT /api/storage/oss/sync`。
- 服务端按文件绑定的固定 objectKey 覆盖对象，不因再次保存生成新路径。
- 服务端上传后立即从同一 objectKey 回读，比较字节数和 SHA-256。
- 回读成功后，服务端在同一次请求中把该文件的 objectKey、ETag、SHA-256 和同步时间写入云端 manifest。
- 只有回读一致才返回 `verified: true`，前端才写入 `synced`、ETag、SHA-256 和同步时间。
- 编辑器明确显示“正在同步 OSS”“已保存并验证 OSS”或“OSS 同步失败”。
- 旧版本中标记为 `synced` 但没有 SHA-256 的记录视为“待云端验证”，刷新后自动重新同步；验证前不显示“本地 + 云端”。
- 在线文档、表格和文本即使标题没有扩展名，也分别导出为 `.docx`、`.xlsx` 和 `.txt`；重命名后自动迁移到与当前标题一致的新 objectKey。

## 验收

选择一个真实 DOCX，在工作台加入唯一测试文字，等待“已保存并验证 OSS”，随后从记录中的同一 objectKey 下载并解析 `word/document.xml`。下载文件必须包含测试文字，并且 OSS 对象大小、ETag 和 SHA-256 与本次上传结果一致。

## 限制

当前 DOCX 导出只保证文字和基础结构，暂不保证完整保留复杂 Word 排版、图片、页眉页脚和批注。
